# Government Construction Project Budget Prediction Using Machine Learning

**Indian government schemes, FY 2025-26** — a Flask + scikit-learn web app that predicts
whether a government construction project will overrun its sanctioned budget, and by how much,
and costs a road corridor between two Indian cities bottom-up from a quantity take-off on a
Leaflet/OpenStreetMap map, with the completion months that corridor takes to build.

Developed by **Vishal Raghunath Chatur** and **Mohsin Jabiulla Balgyar**
Guide: **Tapase Miss**
B.Tech in Artificial Intelligence & Data Science Engineering, **DBATU** — Mini Project

> **Every number on the website is measured.** The metrics tables, confusion matrix, feature
> importances, K-vs-accuracy curve and the per-project risk percentages all come from the two
> pipelines that `model/train.py` actually fits and that `app.py` actually loads from disk.
> Nothing is typed in by hand. What *is* simulated is the dataset itself, and the UI says so in
> three places (hero badge, dataset banner, footer note).
>
> The route planner (§5) is the honest counter-example to "learned": its rupees come from printed
> quantities × printed rates × printed multipliers, its months come from the corridor length ÷ a
> printed km/day construction speed, and its risk grade prints the weights it added
> up. The page labels which number came from data and which came from the engineer's formula —
> including the trained model's cross-check, which warns out loud when a corridor is bigger than
> anything it was trained on.

## 1. Quick start

```bash
pip install -r requirements.txt
py app.py
```

Open **http://127.0.0.1:5000**. That is the whole setup. The route planner is the
**Route planner** nav item, or **http://127.0.0.1:5000/#routes** directly.

`app.py` bootstraps itself: on a fresh clone it generates `data/india_projects_2025_26.csv`
(if missing), trains both models, saves `model/india_knn.joblib`, `model/india_rf.joblib` and
`model/model_meta.json`, builds the partitioned feature store, and then serves. Startup takes
about two seconds and prints a banner with the real measured metrics so you can confirm the
numbers you are looking at are the numbers on disk.

- `python app.py` works the same wherever `python` points at Python 3.10+; on this machine the
  `py` launcher is the reliable one (see §11).
- Tests additionally need Playwright: `py -m playwright install chromium` (§10).
- Nothing in this project reads a `.env` file. Configuration is plain environment variables (§7).

## 2. The dataset (and honestly, how it was made)

`data/india_projects_2025_26.csv` — **700 rows, 10 columns, ₹ lakh**.

It is **synthetic**, generated by `model/generate_dataset.py` (seeded, reproducible:
`py -m model.generate_dataset` rewrites the identical file). Per-project *actual* final
spend for Indian government works is not published as one clean dataset: CAG reports give
audit observations and state-level overrun percentages, GDP/CAG dashboards give aggregates,
and the individual work-order actuals live in state e-procurement portals in inconsistent
formats. So the shape of the data is designed from public findings rather than scraped:

| Design choice | Value | Basis |
|---|---|---|
| Schemes | PMGSY (Rural Roads) 250, PMAY (Housing) 210, Jal Jeevan Mission 145, Smart Cities Mission 95 | Relative prominence of these programmes in central-sector spending |
| Geography | 14 states, 59 districts with a legal state→district map | Maharashtra/Karnataka/Delhi/Uttar Pradesh plus ten more, weighted toward the four named |
| Overrun target | 42.0 % of rows have `actual_cost_lakh > sanctioned_budget_lakh` | General CAG audit finding that cost overruns affect a large minority of works |
| Per-scheme base overrun rate | Different per scheme (roads and water supply worse than smart-city pilot works) | Audit commentary on long linear works |
| Contractor effect | Private-contractor rows overrun more often than Govt-executed rows | Commonly reported implementation gap |
| Overrun magnitude | Mean +13.48 %, median +12.83 % among overrunning training rows; per-scheme means from +7.98 % (Smart Cities) to +18.91 % (JJM) | Kept deliberately modest so the regression heuristic stays sane |

Budgets span ₹ 30.0 lakh to ₹ 22,779.9 lakh (₹ 227.8 crore); durations span 6 to 71 months.
Row counts: `No` 406 / `Yes` 294. Every one of these numbers is recomputed from the CSV at
startup — `tests/test_model.py` asserts the row count, the 42 % ±3 % band, the exact column
list, and that every district is legal for its state.

`data/sample_20_projects.csv` (20 rows, same schema) exists so a reviewer can eyeball real
Indian rows and so it can be fed to the retrain endpoint as a too-small negative test.

### Schema

| Column | Type | Notes |
|---|---|---|
| `project_name` | text | Descriptive Indian work name + work code, e.g. "Vijayawada – Visakhapatnam Rural Road Upgradation … [Work AP-PMGSY-2526-001]" |
| `scheme_name` | category | One of the four schemes |
| `project_type` | category | Road Construction / Housing / Water Supply / Smart City — **not a model feature** (collinear with `scheme_name`) |
| `state` | category | 14 values |
| `district` | category | 59 values, each valid for exactly one state |
| `contractor_type` | category | `Govt` or `Private` |
| `sanctioned_budget_lakh` | float | ₹ lakh, 1 decimal |
| `duration_months` | int | 1–240 accepted, 6–71 present |
| `actual_cost_lakh` | float | ₹ lakh — the "answer" the model predicts the risk of exceeding |
| `over_budget` | category | `Yes` ⟺ `actual_cost_lakh > sanctioned_budget_lakh` — the **target** |

Features fed to the models: `scheme_name`, `state`, `district`, `contractor_type`,
`sanctioned_budget_lakh`, `duration_months` (6 columns → **81** encoded dimensions).

## 3. Models and measured results

Both models are fit on the **same** 80/20 stratified split (`random_state=42`,
560 train / 140 test), through the **same** `ColumnTransformer`:

```
ColumnTransformer(
    [("onehot", OneHotEncoder(handle_unknown="ignore", sparse_output=False), CATEGORICAL),
     ("scale",  StandardScaler(),                                            NUMERIC)],
    remainder="drop")
```

The scaler is fitted on the training rows only — asserted by `tests/test_model.py`, because a
scaler fitted on the full frame leaks test statistics into training.

| Model | Accuracy | Precision (Yes) | Recall (Yes) | **F1 (Yes)** | ROC-AUC | Log loss |
|---|---|---|---|---|---|---|
| K-Nearest Neighbours (k=5, uniform, euclidean) | 0.7357 | 0.6897 | 0.6780 | 0.6838 | 0.8095 | 1.4593 |
| **Random Forest** (300 trees, min_samples_leaf=5, class_weight=balanced, seed 42) | **0.7857** (110/140) | **0.7042** | **0.8475** | **0.7692** | **0.8908** | 0.4661 |

**Winner: Random Forest.** The selection rule is *higher F1 on the `over_budget = Yes` class*,
not accuracy — a classifier that answers "No" for every project scores 0.5786 here, so
accuracy alone would reward a useless model. RF's recall of 0.8475 means it catches
50 of the 59 projects that actually overran in the test split and misses 9; it raises 21
false alarms out of 81 within-budget projects. For a budget department, a missed overrun is
the more expensive error, which is why recall on the Yes class carries the decision.

Random Forest per-class report on the 140 held-out rows:

| | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| No | 0.8696 | 0.7407 | 0.8000 | 81 |
| Yes | 0.7042 | 0.8475 | 0.7692 | 59 |
| macro avg | 0.7869 | 0.7941 | 0.7846 | 140 |
| weighted avg | 0.7999 | 0.7857 | 0.7870 | 140 |

### What the models rely on

Random Forest impurity importances, rolled up per source column:
`contractor_type` **50.79 %**, `state` 16.15 %, `duration_months` 11.0 %,
`sanctioned_budget_lakh` 10.86 %, `district` 7.56 %, `scheme_name` 3.63 %.

KNN has no importances, so the app measures an ablation instead: blank one column at a time
(replace it with its training-set mode) and re-score. Baseline accuracy 0.7357.

| Blanked column | Accuracy | Change |
|---|---|---|
| `contractor_type` | 0.5286 | **−20.71 pp** — by far the strongest signal |
| `duration_months` | 0.6786 | −5.71 pp |
| `scheme_name` | 0.7071 | −2.86 pp |
| `sanctioned_budget_lakh` | 0.7071 | −2.86 pp |
| `state` | 0.7643 | +2.86 pp |
| `district` | 0.7857 | +5.00 pp |

Two of those are **positive**, and the UI prints them in green rather than hiding them:
blanking `state`/`district` makes the KNN *better* on 140 rows. With 81 encoded dimensions
and only 560 training rows, the high-cardinality one-hot columns add distance noise; on a
140-row test split that is worth a few percentage points. It is a real finding, and it is why
the district vocabulary is capped at 59 instead of all ~750 Indian districts.

### K selection

The K-vs-accuracy curve is measured over k = 1…31 on the same split; best observed
**0.8286 at k=25**. The default stays **k=5** because it is the textbook choice students are
expected to defend, and the app shows the curve so the trade-off is visible rather than hidden.
The slider accepts 1–31 (odd values recommended; ties are broken by vote count).

### Prediction outputs

`POST /predict` returns, for the chosen model:

- **verdict** — `OVER BUDGET` or `WITHIN BUDGET` (the class argmax)
- **risk %** — `predict_proba[:, Yes]`. For KNN this is literally the share of the K nearest
  neighbours that overran (the app prints "n over · m within of K" and asserts they agree)
- **predicted actual cost** — `sanctioned × (1 + risk × mean_overrun_pct[scheme])`, a
  **heuristic** clearly labelled as such on the page. It is not a regression model's output:
  it is the model's probability used as a fraction of the scheme's observed average overrun.
  `tests/test_api.py` recomputes that arithmetic from the sanctioned figure and the scheme mean
  and requires the API to match, and asserts the payload itself says "not a regression model".
- **comparable projects** — the K nearest training rows with their distances and outcomes
- **explanation** — sentences naming the mechanism (Euclidean distance vs tree votes), the
  ₹ figures, and the dominant features

Input validation returns **400** with per-field messages: unknown scheme/state/district,
a district that does not belong to the chosen state, a sanctioned budget outside
0.1–1,000,000 ₹ lakh, duration outside 1–240 months, K outside 1–31, non-numeric input.

## 4. Architecture

```
data/india_projects_2025_26.csv          (or an HTTP URL, or an S3 object)
        │
        ▼  StorageAdapter.load(ref) -> DataFrame     data_layer/storage.py
        │    LocalStore | HttpStore | S3Store  — chosen by DATA_STORE env var
        ▼
        │  read_chunks(source, chunksize=250)        data_layer/pipeline.py
        │  map_partitions(enrich_partition, chunks)  — same shape as df.mapInPandas
        ▼
data/feature_store/scheme_name=<scheme>/part-0000N.csv  +  _manifest.json
        │
        ▼  train_and_save()                            model/train.py
model/india_knn.joblib + india_rf.joblib + model_meta.json
        │
        ▼  ModelService (loads artifacts once, serves /predict /metrics /dataset /dashboard)
        │
        ▼  Flask                                       app.py
   / /meta /predict /metrics /dataset /sample.csv /dashboard
   /sources GET+POST /pipeline /pipeline/rebuild /retrain /stream /health
        │
        ▼  single page                                 templates/index.html + static/js/*
   app.js (state, fetch, rendering) · charts.js (every Chart.js instance)
   dashboard.js (aggregates + SSE subscriber) · knn-demo.js (canvas KNN)
```

### `data_layer/storage.py` — one interface, three backends

```
StorageAdapter.load(ref) -> pandas.DataFrame         StorageAdapter.put(df, ref)
  LocalStore   reads/writes only under data/          default
  HttpStore    GETs a public CSV URL, 25 MB cap, read-only
  S3Store      boto3 imported lazily inside the class; creds from the environment
```

`S3Store` is complete code that is never constructed unless `DATA_STORE=s3`. There are no keys
in this repository, so nothing can be pushed by accident, and `put()` additionally refuses
unless the operator sets `ALLOW_WRITES=1`. `GET /sources` reports which adapter is live;
`POST /sources` switches between them and reloads the model service — this is what makes
"API-based data loading" a real code path rather than a paragraph in a report.

### `data_layer/pipeline.py` — Spark-shaped, without the JVM

- `read_chunks()` streams a CSV in `CHUNK_SIZE` partitions: constant memory regardless of file size.
- `map_partitions(fn, chunks)` applies a transform per partition and concatenates. Porting to
  Spark means rewriting that one function body to `spark.sql.DataFrame.mapInPandas`; the
  business logic (`enrich_partition`, which adds `overrun_lakh` and `overrun_pct`) does not move.
- Output is a **partitioned directory plus a manifest**, which is exactly how Spark lays
  parquet out on disk: `data/feature_store/scheme_name=PMGSY_Rural_Roads/part-00001.csv`, with
  `_manifest.json` recording row count 700, chunk size 250, 5 files across 4 partitions, the
  column list, the **sha256 of the source CSV**, `generated_at`, `elapsed_seconds`, and the
  engine string `"pandas-chunked (Spark-shaped: map_partitions + partitioned output)"`.
- Files are `.csv`, not `.parquet`, on purpose: pyarrow is not installed here, and its binaries
  carry the same Smart App Control risk that already bit us on scikit-learn (§11). The manifest
  says so. The writer is a one-line change on a machine where pyarrow loads.
- `load_feature_store()` rebuilds the frame from the partitioned directory and restores the
  true `scheme_name` labels from the manifest (the directory names are sanitised — spaces and
  parentheses become underscores), so round-tripping through the store loses nothing.

### Where a retrain lives

`POST /retrain` accepts an uploaded CSV (or takes the currently-loaded source) and refits both
models in place. A successful retrain writes `data/retrain_active.csv` and `bootstrap()`
prefers it on the next start, so a restart cannot serve the shipped CSV while the metrics on
disk describe your upload. `POST /retrain` with `reset` deletes it. The shipped
`india_projects_2025_26.csv` is never overwritten. Retrains smaller than 30 rows or with only
one class present are refused with **422** and restore the previous artifacts, so a bad upload
cannot leave the site serving a broken model. `sample_20_projects.csv` is the built-in
negative test: 20 rows is below the floor, so the UI refuses it and keeps the 700-row models.

### Real-time dashboard

`GET /stream` is a Server-Sent Events generator backed by an in-process `EventBroker`: every
subscriber gets its own `queue.Queue(maxsize=64)`, `/predict` publishes its result, and a
periodic heartbeat recomputes aggregate KPIs. No message broker, works on Flask's dev server
with `threaded=True` (one thread holds the SSE connection while others answer `/predict`).
The dashboard de-duplicates on the event `sequence` number. Slow consumers lose events rather
than blocking the predictor — documented, intentional.

## 5. Route planner — costing a corridor on the map

`model/route_engine.py` answers a different question from `model/train.py`. The classifiers say
*"will this sanctioned project overrun?"* from data; the route engine says *"what would this road
cost, how long would it take, and out of what?"* from an engineering quantity take-off and a stated
construction speed. **Nothing in it is learned**: the rates are documented FY 2025-26 assumptions,
and every response carries a `basis` sentence saying
so, so nobody has to guess which side a rupee figure came from.

### 5.1 Distance is measured, then calibrated — never typed per pair

`CITIES` holds 56 districts — 56 of the 59 the trained models know, the three missing ones being
East Delhi, North-East Delhi and Ghaziabad — each with latitude, longitude, default terrain and
default soil. Great-circle distance is haversine on a 6371 km sphere. Roads do not follow great
circles, so one number converts the two:

```
CORRIDOR_FACTOR = 1.151 = median(published road km ÷ straight-line km) over 17 routes
```

| Corridor | Engine | Published | Error |
|---|---|---|---|
| Nashik → Pune | 189.2 km | 199 km | −4.9 % |
| Mumbai City → Pune | 138.3 km | 149 km | −7.2 % |
| Pune → Nagpur | 713.8 km | 620 km | +15.1 % |
| Ahmedabad → Vadodara *(worst)* | 116.5 km | 101 km | +15.3 % |

Median absolute error 2.9 %, mean 4.6 %. `tests/test_routes.py` fails if any calibration route
drifts more than 16 % from its published figure — that is what keeps a "roughly 200 km" claim
honest instead of hard-coding one famous pair and letting the rest of the map drift. A length
typed from a DPR overrides the calibrated one, and `distance_basis` then reports "the length
typed in the request replaced it" rather than continuing to claim the calibration.

### 5.2 Cost is assembled bottom-up

```
Total = Σ ( quantity × unit rate ) × terrain factor × soil factor × 1.18
        └─ quantities from cross-section × length ─┘   └─ site ─┘  └ overheads ┘
```

The take-off is rupee-free — square metres of carriageway (`width × 1000 × km`), cubic metres of
pavement and GSB, tonnes of aggregate/sand/bitumen, bags of cement, tonnes of steel, person-days,
machine-hours, drain-lines — and each line is multiplied by one published rate:

| Rate | ₹ | Rate | ₹ |
|---|---|---|---|
| Cement (50 kg bag) | 350 | GSB | 640 / m³ laid |
| Steel (TMT Fe500D) | 60 000 / t | Earthwork cut + fill | 210 / m³ |
| Bitumen (VG-30) | 50 000 / t | Labour | 650 / person-day |
| Aggregate (10–20 mm) | 1 250 / t | Machinery | 1 450 / machine-hour |
| M-sand | 900 / t | Shoulders + furniture | 1.2 lakh / km·m |
| Cross drainage | 7.5 lakh / line-km | Overheads | 18 % |

Worked example, Nashik → Pune as a 7 m rural two-lane through ghat in black-cotton soil
(189.2 km, site factor 1.30 × 1.10 = 1.43):

| Item | ₹ crore | Item | ₹ crore |
|---|---|---|---|
| Aggregate | 164.06 | Bitumen | 47.35 |
| Labour | 56.28 | Sand | 50.62 |
| Sub-base GSB | 24.24 | Steel | 4.06 |
| Cross drainage | 20.29 | Earthwork | 13.92 |
| Shoulders + furniture | 16.23 | Machinery | 11.77 |
| Cement | 1.99 | **Works + 18 % overheads** | **484.75** |

₹ 2.562 crore per km, ₹ 101.70 crore of which is the ghat and ₹ 44.07 crore the soil.

Terrain multipliers: plain 1.00, **urban 1.15**, coastal 1.15, hilly and rocky/hilly 1.25,
**ghat 1.30** — the brief's "ghat +20–30 %", taken at the top of that band because the ghat
sections around Nashik and Pune are rock-cut, not merely winding. Soil multipliers: alluvial 1.00,
red/laterite 1.05, rocky 1.08, black-cotton 1.10, sandy 1.12, soft clay 1.15. Both are auto-detected
from the two cities (worse of the two wins) and both are overridable in the form.

### 5.3 Two ways to get a total, and which one the page shows

`DEFAULT_COST_PER_KM_CRORE = 2.0` is the brief's simple `Budget = Distance × Rate`. Left blank, the
form uses the itemised take-off. **Type a rate and it becomes authoritative**: the total is exactly
distance × rate, and the component rows are rescaled to it — each row is tagged "share rescaled"
and the note reads "the total is your assumption, the proportions are the engineer's". The
unforced figures survive beside it as `takeoff_total_crore` / `takeoff_cost_per_km_crore`, so
forcing ₹2 crore/km on Nashik → Pune shows ₹ 378.40 crore next to the ₹ 484.75 crore take-off
instead of quietly overwriting it.

### 5.4 Completion time: the same distance divided by a stated speed

`construction_time()` is the brief's `Time = Distance ÷ Construction Speed` with three bands and
nothing else:

| Band | km per day | Applies to |
|---|---|---|
| Highway | 3–5 | `national_highway_4`, `expressway_6` |
| Rural road | 1–2 | `state_highway`, `rural_two_lane` |
| Ghat / hilly | 0.5–1 | any `ghat`, `hilly` or `rocky_or_hilly` corridor, **overriding** the cross-section |

The likely figure divides the length by the band midpoint and converts at
`DAYS_PER_MONTH = 365.25 / 12` (30.44 calendar days); `min_months` and `max_months` use that band's
own fastest and slowest speeds, so the range on the card is exactly the range the stated assumption
allows — no hidden slack:

- Nashik → Pune, 189.2 km of ghat: `189.2 ÷ 0.75 km/day = 252 calendar days = 8.3 months`, band
  **6.2–12.4**, card reads "8 months (6.2–12.4)". The brief's worked example (200 km, ghat,
  "~6–10 months") comes out at 8.8 months with a 6.6–13.1 band — the same arithmetic at the longer
  length it typed.
- The same 200 km as a 4-lane national highway on plain ground is 1.6 months (1.3–2.2), because the
  only thing that changed is the band. A test pins both.

Urban working costs **time** as well as money: `URBAN_TIME_FACTOR = 1.15` multiplies the day count
(traffic diversions, night working and utility shifting consume calendar time, not just rupees),
which is why the brief's "+15 % urban" is charged in both places rather than only in the cost table.

Two time figures, deliberately different and both labelled on the page:

| Figure | Source | Meaning |
|---|---|---|
| `time_months` / `construction_time` | length ÷ band speed ÷ 30.44 days | the plant laying the carriageway — what `/predict-route` returns and the card prints |
| `planned_duration_months` | `MONTHS_PER_KM` 0.16–0.45 by cross-section ×1.35 ghat ×1.20 hilly, clamped 6–240 | the contract programme, and the field `model_input` hands the classifier |

The gap is real and not an error: Nashik → Pune builds in 8 months of continuous working inside a
46-month programme, because acquisition, utilities, statutory clearances, mobilisation and defect
liability are most of an Indian highway contract. A test asserts runtime < programme, so the two can
never silently converge. The runtime figure carries no monsoon shutdown, no land-take phasing and no
bridge or tunnel critical path — stated in §12 rather than hidden in the formula.

Where it appears: the "Completion time" card (whose tooltip *is* the printed `basis` string), the
"Time basis:" sentence in the note under the results, the **Budget versus time** chart (month bars
against a ₹ crore line, over all 17 calibration corridors), and both the CSV and PDF exports.

### 5.5 Risk: a stated weight sum, with the trained model next to it

`risk_percent` is deterministic arithmetic, not a probability: base 12 + terrain 6…22 + soil excess
(factor − 1) × 100 × 0.6 + complexity 3…10 + length 0/4/8, clamped to 5–75 %, banded
Low < 25 ≤ Medium < 45 ≤ High. The response prints the weights it added up. Separately,
`model_check` is a **real prediction** from the trained Random Forest (or KNN on request) for a
sanctioned work of that size, and it is honest about its own limits: the largest project in the
700-row training set is ₹ 227.80 crore, so the Nashik → Pune corridor returns
`within_training_range: false` and a note saying the model is extrapolating — "an order-of-magnitude
guide, not a probability". Because that cross-check is a genuine model call, it also appears in the
live SSE feed and increments `predictions_served`; that side effect is asserted by a test rather
than hidden.

### 5.6 The map

Leaflet 1.9.4 (BSD-2, public CDN) over OpenStreetMap tiles — no API key, no paid service, nothing
to bill. 56 city markers around a Maharashtra-centred view, a corridor polyline drawn from the
`route_path` the API measured (25-point geodesic; it bows up to 35 km away from the straight
lat/lon line on the longest diagonals of the catalogue, and under 5 km on the 17 calibration
corridors, which is why the map is redrawn from the response rather than from a guess), one marker
per endpoint, and the line recomputed on swap. Tiles © OpenStreetMap
contributors. If the CDN is unreachable the card shows an on-page fallback that names the file to
make reachable, and every number still comes from Flask, so the planner works offline apart from
the basemap itself. Dark mode dims the tiles with a CSS filter instead of switching tile servers.

### 5.7 Location hierarchy: State → District → Taluka → Village

The brief asks the planner to take a *village*, not a city. `model/planning_data.py`
generates `data/india_road_project_planning_dataset_2025_26.csv` — 504 rows with exactly the
17 columns the brief lists (`state, district, taluka, village, lat, lng, road_type, terrain,
soil_type, distance_km, budget, time_months, cement_cost, steel_cost, bitumen_cost,
labor_cost, machinery_cost`). It is written once, on first boot, from a seeded generator, so
`py model/generate_dataset.py`-style reproducibility applies here too: 14 states × 56 districts
× 3 talukas × 3 villages, identical rows on every machine.

**What is real and what is a placeholder** — said on the page, in `/locations`, and here:

| Field | Source |
|---|---|
| State, district names | The same 56-district vocabulary the trained models and `CITIES` use |
| District lat/lon | Real district headquarters coordinates |
| Taluka, village names | **Generated placeholders** from a Maharashtra-style name pool |
| Village lat/lon | 2–35 km from its district headquarters at a seeded bearing |
| Terrain, soil | Inherited from the district's own catalogue entry — never randomised, so landlocked Agra is never "coastal" |
| `distance_km` | Haversine (village → district HQ) × `CORRIDOR_FACTOR` 1.151 — the same coefficient §5.1 calibrates |
| `budget` + the 5 material columns | One call to the §5.8 formula at the row's own road type, terrain and soil |

`GET /locations` returns that tree (14 states, 56 districts, 168 talukas, 504 villages) and
answers `?q=` with village/taluka/district/state matches, each carrying its connector distance,
budget, months and risk band so the suggestion list is already useful.

The four dropdowns on both ends are **dependent**: choosing a state refills the districts and
*clears* taluka and village, so the four names can only ever spell a path that exists in the
dataset. The server resolves the deepest level actually named:

- a village → that village's own coordinates;
- a taluka with no village → the taluka office;
- a district with no village → **its headquarters**, and the readout says so out loud rather
  than pretending a village was chosen;
- a village name that repeats inside its own district (33 of them do) with no taluka chosen →
  refused, with a message naming the taluka to pick. Falling back to the district headquarters
  there would silently price a road to somewhere the reader did not choose.

`POST /predict-route` therefore accepts either two city names or two nested objects:

```json
{"start": {"state": "Maharashtra", "district": "Pune", "taluka": "Arasgaon Bk", "village": "Ghoti"},
 "end":   {"state": "Maharashtra", "district": "Nashik"},
 "road_type": "rural_two_lane"}
```

One nested end and one city end is a 400 ("name both ends the same way"), identical ends are a
400, and an unknown village is a 400 on `start_village` / `end_village`. A village corridor
reaches the *same* take-off engine as a city corridor: the only difference is that its length is
measured from the two coordinates instead of looked up from the calibration table, and
`_relabel_for_hierarchy` rewrites the fields that would otherwise name a city — including the
`model_input` state and district the trained classifier is asked about, so the §5.5 cross-check
stays a genuine model call for village-to-village works too.

### 5.8 The planning formula: a second, deliberate view of the same road

`model/planning.py` implements the brief's one line:

```
Total = Distance × Base ₹ per km × Road width factor × Terrain factor × Soil factor
```

| Road class | Base ₹ crore / km | km per day | | Factor | Value |
|---|---|---|---|---|---|
| Rural 2-lane | 1.00 | 2 | | Ghat / hilly | ×1.30 |
| National/state highway | 2.00 | 4 | | Urban / city | ×1.15 |
| Expressway | 5.00 | 4 | | Rocky | ×1.20 |
| | | | | Clay | ×1.10 |
| | | | | Sandy | ×1.05 |

Road width is normalised to its class standard (3.75 / 7 / 14 m) and clamped, so a 24 m
carriageway on a rural cross-section raises the bill instead of silently being ignored. The
material split is the brief's 25 / 20 / 15 / 20 / 20 % (cement, steel, bitumen, labour,
machinery) and the five lines are summed from the *rounded* rupee figures with any rounding
residual pushed into cement, so they add back to the printed total to the rupee.

Worked example — the corridor the page opens on, Ghoti (Arasgaon Bk taluka, Pune) to Nashik,
7 m rural two-lane, ghat terrain, clay soil, measured 202.6 km:

```
202.6 km × ₹ 1.0 crore/km (rural base) × 1.000 width (7.0 m ÷ 7 m) × 1.30 terrain × 1.10 soil
  = ₹ 1.43 crore per km  =  ₹ 289.72 crore  =  ₹ 28,971.80 lakh
Cement 7,242.95 · Steel 5,794.36 · Bitumen 4,345.77 · Labour 5,794.36 · Machinery 5,794.36 lakh
202.6 km ÷ 1.0 km per day (Ghat / hilly) = 203 working days ÷ 30.44 = 6.7 → 7 months
₹ 289.72 crore sits between 200 and 500 → Medium risk by sanction size
```

**Why the page shows two totals for one road.** §5.2's take-off is bottom-up — quantities from
the cross-section × published unit rates. §5.8 is top-down — the whole corridor at one assumed
₹ per km for its class. The same corridor comes out at ₹ 519.09 crore and ₹ 289.72 crore, and
that is the honest answer, not an error to be reconciled: a DPR rate and a quantity estimate
disagree in real practice, so both are printed, each with the arithmetic that made it, and the
panel says in words that the second "is a different measurement from the quantity take-off, not
a check on it". Risk is reported twice for the same reason: `risk_percent` (§5.5) is a stated
weight sum, `planning.risk` is the brief's sanction-size threshold.

`planning.materials` is returned as an **ordered list**, not a mapping, because Flask sorts JSON
keys on the way out — a dict would reach the browser alphabetically and the five lines would
lose the order the brief states. `tests/test_planning.py` pins that.

### 5.9 `/building` — the second estimator, kept genuinely separate

`templates/building.html` + `static/js/building.js` + `model/building.py` + `POST
/predict-building`. The dashboard, the road planner and every existing endpoint are unchanged;
the building page reuses `/locations` read-only for its cascade and shares nothing else with the
route system except the ₹ formatting convention. It does not ask the trained classifier
anything: that model was fitted on sanctioned *scheme* projects, not on a 1,200 sq ft panchayat
office, and inventing a "prediction" for it would be exactly the faked metric this project
avoids. The response therefore carries no `probability`, and the card says it is a rate-based
estimate.

```
Total = Built-up area × ₹ per sq ft (location) × Floor factor × Location factor
                       × Quality factor × Building type factor
```

| Input | Values |
|---|---|
| Location type | rural ₹ 1,500/sq ft · urban ₹ 2,500 · **remote ₹ 1,800** (documented middle case: haulage + mobilisation, without urban labour rates) |
| Storeys | 1 × 1.00 · 2 × 1.90 · 3 × 2.65 — the foundation, staircase and plot works are paid for once |
| Quality | low × 0.85 (55 sq ft/day) · medium × 1.00 (45) · high × 1.25 (35) |
| Building type | Gram Panchayat × 0.90 · School × 1.00 · Hospital / urban health centre × 1.35 |

Two worked examples, both straight from the endpoint:

```
1200 sq ft × ₹ 1500 × 1.00 floors × 1.00 location × 1.00 quality × 0.90 type = ₹ 16.20 lakh
   1200 sq ft ÷ 45 sq ft/day + 120 days site set-up = 147 days ÷ 30.44 = 4.8 → 5 months

6000 sq ft × ₹ 2500 × 1.90 floors × 1.00 location × 1.25 quality × 1.35 type = ₹ 4.81 crore
   11,400 sq ft ÷ 35 sq ft/day + 120 days = 446 days ÷ 30.44 = 15.8 × 1.08 sequence = 16 months
```

Time is driven by the *area actually raised* (`area × floor factor`), plus 120 fixed days of
site set-up that a 600 sq ft office still needs, with a 3-month floor — a rate an order of
magnitude higher would print a completion time no site engineer would sign. The cost splits
across seven work sections (structure 42, masonry 12, finishes 15, electrical+plumbing 11,
labour 12, fixtures 6, site development 2 = 100 %), again with the rounding residual absorbed
by the largest line so the table adds to the card to the rupee — and the browser sums the rows
it printed rather than reprinting the total, so a reader can check one against the other.

## 8. Currency and visual identity

**One rule, one implementation each side.** `formatINR(lakh)` in `static/js/app.js` and
`format_inr()` in `app.py`/`train.py`:

```
< 100 lakh          → ₹ 45.6 lakh
≥ 100, < 100000     → ₹ 4.56 crore
≥ 100000 lakh       → ₹ 456 crore      (1 crore = 100 lakh)
```

**No `$` appears anywhere** — not in the UI, the JSON API, the CSV exports, or the PDF.
`tests/test_api.py` and the smoke test both assert it by scanning rendered text and payloads,
including the lakh/crore boundaries at 99.9 / 100 / 100000. One exception is documented in the
PDF: jsPDF's built-in Helvetica has no rupee glyph, so the PDF writes `INR` rather than
emitting a tofu box. The website itself always shows ₹.

Tricolour, kept accessible: navy `#0A1F44` is the base (the Ashoka chakra is itself navy),
saffron `#FF9933` is an **accent only** — borders, chart series, focus rings, large headings.
Green `#138808` marks the "within budget" verdict. Any saffron or green that carries body text
is darkened to `#B25A00` / `#0B6B0B`, because the raw flag hues fail contrast on white. Dark
mode is a class toggle persisted in `localStorage["budget-theme"]`; charts re-sample the CSS
custom properties and repaint on toggle.

## 12. Assumptions & limitations

1. **The dataset is simulated** (§2). Scheme mix, base overrun rates and the 42 % target are
   design choices informed by general CAG audit findings, not measured statistics.
2. All money is ₹ lakh with one decimal; 1 crore = 100 lakh.
3. Districts are capped at 59 so district-level one-hot encoding stays statistically
   meaningful — real Indian project data covers far more, and the ablation shows high
   cardinality actively hurting KNN here.
4. `project_type` is excluded from features because it is a 1:1 function of `scheme_name`.
5. **Random Forest instead of XGBoost**, for the same binary-compatibility reason as §11.
6. Probabilities are model-native and **not calibrated** (no isotonic/Platt step at this scope).
   KNN's log loss of 1.4593 vs RF's 0.4661 is the visible cost of that.
7. The predicted ₹ figure is a labelled heuristic, not a second trained regressor.
8. No Spark/JVM, no pyarrow, no boto3 installed here: the S3 and Spark paths are
   code-complete but **unexercised on this machine** and tested against local stubs.
9. SSE is single-process. Two app instances would each see their own predictions until the
   broker is swapped for Kinesis/SNS.
10. Metrics are from one 80/20 split with a fixed seed. Cross-validation would tighten the
    confidence intervals; the 140-row test split means a few percentage points of the
    comparison is sampling noise — stated in the UI's limitations panel, not just here.
11. **The route planner is an engineering estimate, not a tender estimate** (§5). One corridor is
    priced at one cross-section: no land cost, no utility shifting, no structures/tunnelling, no
    bridge or culvert counts, no state-wise GST or MOQ variation, and no seasonal rate movement.
    The unit rates and the terrain/soil multipliers are published 2025-26 assumptions, and the
    payload labels them as assumptions in `basis` rather than presenting them as measurements.
12. Corridor distance is a single median factor over 17 published routes, so it fits most pairs to
    within a few percent and the two near-straight ones (Ahmedabad–Vadodara, Pune–Nagpur) to within
    ~15 %. The polyline is a geodesic between two cities, **not a surveyed alignment** — the map
    card says so under the tiles.
13. The trained-model cross-check on a route is extrapolation for any corridor above
    ₹ 227.80 crore (the largest sanctioned project in the 700 rows). The response flags it with
    `within_training_range: false` and the UI repeats the warning instead of showing a confident
    percentage.
14. **Completion time is a stated speed, not a schedule** (§5.4). Three km/day bands, calendar days
    at 30.44, and a 1.15 urban drag: no monsoon shutdown, no land-acquisition phasing, no bridge or
    tunnel critical path, and no mobilisation/demobilisation float. Treat the printed band
    (e.g. 6.2–12.4 months) as the range the assumption allows rather than a forecast, and note that
    it is a different quantity from the `planned_duration_months` contract programme the classifier
    is fed — the page prints both, labelled.
15. The v1 Thai-paper version is preserved in `archive/thai-paper-version/` for history.
    Nothing loads it; there is no paper-comparison panel left in the India build.

16. **Taluka and village names in the planning hierarchy are generated placeholders** (§5.7),
    around real district-headquarters coordinates: 168 taluka and 504 village names are drawn from
    a Maharashtra-style pool and 33 village names repeat inside their own district, which is why a
    bare village name is refused rather than guessed at. Districts, coordinates, terrain and soil
    are the real catalogue the engines use. The page, `/locations` and this README all say it;
    a viva answer about "which village is that" should give this answer, not a shrug.
17. The planning formula and the quantity take-off disagree on purpose (§5.8) and their soil tables
    differ: `route_engine` charges sandy 1.12 / clay 1.15 while `planning` charges rocky 1.20 /
    clay 1.10 / sandy 1.05, because one is a materials estimate and the other is the brief's
    per-km rate. Same seven keys on both sides, asserted by a test, no attempt to reconcile the
    numbers.
18. **`/building` is a rate table, not a model** (§5.9). One ₹/sq ft per location type times five
    published factors, and it prices one standard structural frame: no land, no boundary wall, no
    furniture, no specialist medical equipment, no earthquake design premium, no state-wise
    contractor rates. Its response carries no probability because the classifier was never trained
    on buildings, and the card that prints it says so.
19. The building time model charges 120 fixed site days whatever the area, so a 100 sq ft
    panchayat office prints ~4 months. That is the honest shape of the assumption — mobilisation
    does not scale with floor area — and the floor is stated as 3 months, not hidden.

## 13. Viva preparation — 15 questions and their real answers

**Q1. Why Random Forest over KNN here?**
Higher Yes-class F1 (0.7692 vs 0.6838), higher recall (0.8475 — it catches 50 of 59 real
overruns), and far better probability quality (log loss 0.4661 vs 1.4593). KNN's 81-dimensional
one-hot space makes Euclidean distance mostly measure *which district you are in* rather than
*spend behaviour*.

**Q2. Why choose by F1 on the Yes class instead of accuracy?**
A model that always answers "No" gets 0.5786 accuracy on this test split — 57.9 % while
predicting nothing. Overruns are the minority class and the expensive error, so the minority
class F1 is the honest comparison.

**Q3. Why one-hot encode and standard-scale together?**
One-hot makes categories honestly comparable (Pune is not "twice" Nashik); StandardScaler puts
₹ lakh and months on the same numeric footing so KNN's distance is not dominated by the
larger-scaled column. The scaler is fitted on training rows only, otherwise test statistics
leak into the fit.

**Q4. Where does the risk percentage come from?**
`predict_proba`. For Random Forest it is the fraction of the 300 trees voting Yes, weighted by
`class_weight="balanced"`. For KNN it is literally the share of the K nearest neighbours that
overran, which the UI prints as "n over · m within of K" and the tests assert it agrees.

**Q5. Is the predicted ₹ cost a model output?**
No, and the page says so. It is `sanctioned × (1 + risk % × scheme mean overrun %)`, using the
13.48 % overall / 7.98–18.91 % per-scheme averages measured from training rows. A classifier
gives a probability, not a rupee figure; this converts one into the other transparently.

**Q6. What is your data source?**
A synthetic dataset modelled on CAG-reported overrun patterns, because per-project actuals are
not published as one clean file. Generator is seeded and reproducible; the UI, README and
export all disclose it. That is a limitation we chose to state rather than hide.

**Q7. Explain the confusion matrix.**
Out of 140 held-out projects: 50 overruns caught, 9 missed, 60 within-budget correctly cleared,
21 false alarms. 110 correct → 0.7857. For an audit department the 9 misses are the risk; the
21 false alarms cost a review meeting.

**Q8. What does your "cloud" architecture actually do?**
A `StorageAdapter` interface with local/HTTP/S3 implementations swapped by environment variable,
and a chunked `read_chunks`→`map_partitions`→partitioned-output pipeline shaped like
`spark.mapInPandas` writing a manifest-backed feature store. S3 needs credentials from the
environment plus `ALLOW_WRITES` for any write; nothing is committed.

**Q9. Why is the feature store CSV and not parquet?**
pyarrow's binaries hit the same Windows Smart App Control block as scikit-learn 1.9, so the
partitioned layout is real while the format stays CSV. The manifest records the engine, chunk
size, row counts and the sha256 of the source, and `to_parquet()` is a one-line swap.

**Q10. What would you improve first?**
Real project-level data, then cross-validation over a single 140-row test split — the current
gap between k=5 (0.7357) and k=25 (0.8286) is partly sampling noise, and calibration, because
KNN's log loss shows its percentages are not trustworthy as probabilities.

**Q11. Your route planner gives a rupee figure with no training data behind it — why should we
believe it?**
Two reasons, and both are on screen. Distance is *measured* and then checked: one corridor
coefficient is the median of the ratio between 17 published Indian road distances and their
great-circle distances, and a test fails if any of those 17 drifts more than 16 % — Nashik→Pune
comes out 189.2 km against 199 published. The money is a bottom-up take-off: bags, tonnes, cubic
metres, person-days from the cross-section and the length, each multiplied by one printed rate, so
a reviewer can disagree with a single line instead of the whole number. What is *not* claimed is
learning — the risk grade prints the weights it added, and the trained model's own answer is shown
separately with an extrapolation warning the moment a corridor exceeds the largest project in the
training data.

**Q12. How do you get an completion time, and why does the page show two different month figures?**
`Time = Distance ÷ Construction Speed`, with the speed taken from the three published bands the
brief names — highway 3–5, rural 1–2, ghat/hilly 0.5–1 km per day — and the hilly band *overriding*
the cross-section, because a 4-lane ghat section is still laid at ghat speed. Nashik→Pune is
189.2 km ÷ 0.75 km/day (the band midpoint) = 252 calendar days = 8.3 months, and the card prints
"8 months (6.2–12.4)" where the band is that same division at the band's own fastest and slowest
speeds — so the range shown is exactly the range the assumption permits, and a test fails if the
printed months ever stop matching the arithmetic printed beside them. The second figure,
`planned_duration_months`, is the **contract programme** (0.16–0.45 month/km by cross-section,
×1.35 for ghat) and is what the classifier's `model_input` consumes; 8 months of continuous laying
inside a 46-month contract is normal in India because acquisition, utilities, statutory clearances
and defect liability are most of the programme. The two are kept apart and labelled instead of one
of them being quietly passed off as the answer.

**Q13. The planner has two corridor pickers and four dropdowns per end — why, and are those
village names real?**
City mode is the original 24-node picker; hierarchy mode is the brief's State → District →
Taluka → Village cascade, both ends, fed by one free endpoint (`GET /locations`) that returns
**14 states · 56 districts · 168 talukas · 504 villages** — 3 talukas per district, 3 villages per
taluka. Provenance is split and printed on the page: the 56 **district centres carry real
coordinates, terrain and soil** because those are what the distance model consumes, while the
taluka and village *names* are generated placeholders seated 4–55 km from their district centre.
There is no free, complete, coordinate-level village gazetteer for India (the revenue-cadastre
snapshots stop at sub-district and are not redistributable), so inventing the leaf names and
labelling them was the honest option — the disclosure sits next to the dropdowns and a browser
check fails if the word "placeholder" ever disappears from it. Nothing is hardcoded per pair: even
a village corridor is Haversine from the district centre to the seated point × the calibrated
1.1510, and the selector resolves ambiguity rather than guessing — a name repeated inside the
chosen district raises *"'Kusumta' is in more than one taluka of Pune — choose the taluka as
well"* instead of silently pricing the wrong hamlet.

**Q14. Brief A hands you one formula. Your page shows two different totals for the same road.
Why not just use the formula?**
We kept both, side by side, and said which is which. The brief's top-down rule
(`Distance × base rate/km × width × terrain × soil`, then 25/20/15/20/20) is implemented exactly as
written in `model/planning.py` and printed in its own panel with the multipliers it used, so a
reviewer can check one line. The headline number is still the bottom-up take-off from
`model/route_engine.py` (bags of cement, tonnes of steel, cubic metres, person-days × printed unit
rates), because a rate-per-km cannot express a cross-section and it under-prices short hill
connectors. The two disagree by design — a formula calibrated on average national spend versus an
itemised bill for one specific corridor — and the panel prints the gap as a sanity range instead of
averaging the two into a number that means neither. Attaching the formula as a separate `planning`
key also meant `/predict-route`'s existing contract stayed byte-identical: the five keys the first
version returned are still those five, so no earlier test or screen had to change. One difference
to expect rather than discover: the two soil tables are *not* the same (planning uses rocky 1.20 /
clay 1.10 / sandy 1.05 exactly as briefed; the take-off uses its own measured soil factors), and
§12 lists that as an assumption instead of hiding it.

**Q15. `/building` looks like the same app in a new coat — how is it a separate system, and why is
there no risk percentage on it?**
Separate template (`templates/building.html`), separate controller (`static/js/building.js`),
separate engine (`model/building.py`), separate endpoint (`POST /predict-building`); the only thing
it shares is the read-only `/locations` hierarchy. No existing route, file or response was touched,
and a browser check asserts `window.App` is **undefined** on `/building` — proof the main front-end
bundle is not loaded there. The estimator is the briefed `Area × ₹/sq ft × floor × location ×
quality` (Rural ₹1,500 / Urban ₹2,500 / Remote ₹1,800 base, 7-work split summing to exactly 100 %
and to exactly the printed ₹ lakh total) plus `Time = Area ÷ sq-ft-per-day + 120 mobilisation days`.
There is no probability because there are no building rows to learn from: the trained classifier's
contract is the 10-column scheme-work CSV (`data_layer/schema.py`) and it has no `area_sqft`,
`floors` or `quality` column, so a "% risk" on that page would be decoration. What it prints
instead is the arithmetic — every factor that multiplied, the ₹/sq ft it started from, and a note
that land, furnishing and statutory contingencies are excluded. Same rule as everywhere else in the
app: a rate table is shown as a rate table.
